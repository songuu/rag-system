# 问答入口能力路由

问答入口不能把所有非固定问候都当作文档问题。当前同步接口在请求校验和鉴权之后、访问向量服务之前，执行 `conversation-router/v1`。前端待处理状态和向量服务可用性检查复用相同路由。

`src/app/api/ask/route.ts` 仅加载校验、鉴权和直接回答工具；需要 RAG 时才动态导入 `runtime.ts`，将已经校验的请求与身份一起交给原工作流。直接请求不会初始化模型 SDK 或 Milvus。`lightweight-entry.test.mjs` 在任何直接入口导入模型 SDK、Milvus 或 RAG 运行时时失败，以防依赖边界退化。GET/PATCH 继续转交持久化工作流的现有实现。

构建层使用 Next 的稳定 `serverExternalPackages` 配置，将 LangChain 与 Milvus SDK 交给 Node 原生加载，避免首次 API 编译深入其依赖图。这是服务端配置；不会把模型 SDK 加入浏览器直接问答路径。参见 [Next 官方配置说明](https://nextjs.org/docs/app/api-reference/config/next-config-js/serverExternalPackages)。

## 路由策略

1. 统一 Unicode、空白、标点与礼貌表达。
2. 明确文档范围或解释性要求优先保留知识库路径。
3. 解析完整请求的受支持能力与参数：日期、时间、星期、昨日/明日、已知时区、算术、助手身份/能力、当前模型配置。
4. 对复合请求逐段解析。仅当全部子请求都有可执行能力时才跳过检索；不能只回答第一部分。
5. 对尚未识别的短请求，使用小模型进行有预算的语义分类；分类必须完整覆盖请求，输出只允许已登记的动作与参数。分类失败、未知动作、非法参数或混合文档问题保留原 RAG 流程。

语义分类使用操作员配置的 `FAST_LLM_MODEL`（默认 `qwen2.5:0.5b`），限时 2.5 秒、温度为 0、JSON Schema 输出，并在服务端再次校验。模型只选择能力，日期仍由系统时钟计算，算术仍由有限语法解析器执行。响应明确提供 `routingModel`，并将分类模型调用计入 `modelUsage.llm`。远程提供商默认不使用这一 Ollama 分类器；可通过 `RAG_SEMANTIC_ROUTER=off` 关闭。参见 [Ollama 结构化输出](https://docs.ollama.com/capabilities/structured-outputs)。

| 回答类型 | 可信来源 | 调用模型/向量服务 |
| --- | --- | --- |
| 日期、时间、星期 | 服务端系统时钟、IANA 时区 | 否 |
| 独立算术 | 有限长度/深度/数值范围的算术语法解析器 | 否 |
| 当前模型 | 当前请求已验证的模型选择 | 否 |
| 问候、身份、功能 | 助手的固定能力说明 | 否 |
| 实时天气、行情、新闻 | 当前没有接入相应实时源，明确说明缺失能力 | 否 |
| 文档、解释或不明确的问题 | 已授权知识库与现有 RAG 策略 | 按原策略 |

实时问答不缓存答案：响应设置 `Cache-Control: no-store`。响应提供 `routing`、`answerSources` 和各阶段处理说明，不提供模型内部推理。工具路径不绕过模型白名单、鉴权或请求取消。持久化执行模式保留原有工作流与幂等协议。

## 边界

- 默认北京时间；支持北京/上海/中国、东京/日本、伦敦、纽约和 UTC。未知时区不会猜测。
- 昨日/明日按目标时区的日历推进，避免夏令时跨日误差。
- 算术支持数字、括号、一元正负号、加减乘除和余数。拒绝变量、代码、过深/过长表达式和超出安全数值范围的结果；小数使用 JavaScript 数值语义，适合基础计算。
- 未接入实时互联网来源时不生成看似实时的天气或行情。URL 导入文档不能代替实时查询。
- 路由由确定性解析和受限语义分类组成；未知问法仍可能进入 RAG，不能将回归通过率当作任意语言的理解准确率。
- 新增能力时先增加正例、同义改写、知识库反例、参数边界与鉴权回归，再登记执行器。

## 模型准备与超时

- LLM 切换只校验当前请求的模型配置，不同步加载大模型或重建知识库。刷新健康信息不会覆盖会话选择。Ollama 模型列表按模型名称与默认标签合并同名迁移条目，隐藏内部 `llamacpp:<digest>` runner，保留非默认标签的完整名称。
- 更换 Ollama 向量模型时，`/api/model-selection` 校验 `reindex` 权限后返回 `202` 后台任务；页面轮询并显示已处理的文档块。任务以限定知识库范围读取所有原始文档块，在独立 Milvus 集合重新向量化，用真实输出维度创建索引。强一致逻辑计数核对完整数量，并复核源快照未变化，成功后才将活动模型、集合与维度一起写入 PostgreSQL。原集合保留，失败不发布半成品；服务重启通过 instrumentation 恢复活动指针。任务状态与导入互斥当前沿用项目的单进程协调方式，不声称跨副本协调。
- 嵌入切换任务最长 30 分钟，单次模型请求最多 10 分钟；重启后的未完成任务需要重新发起。向量模型选择不会修改环境文件或模型白名单。切换的是当前知识库的向量索引，LLM 仍为会话选择；旧页面继续提交旧嵌入模型时会收到明确的刷新提示。
- `/api/model-warmup` 的 POST 在鉴权与模型白名单校验后立即返回 `202` 和 `loading`，GET 提供鉴权后的加载状态。后台使用空提示预加载；相同任务合并，最多 4 个并发装载，最多保留 64 个状态，装载期限为 10 分钟。作业是进程内状态，重启后需要重新预加载。Ollama 自身的加载期限仍由运行它的进程决定。
- 页面轮询状态，切换时忽略旧模型的迟到响应；失败显示明确原因并允许重试。加载中的同步知识库请求返回 `MODEL_LOADING`，工具问答仍可用。页面打开时每 5 分钟续期，页面关闭后保留期有限。
- 预加载与生成共享 `OLLAMA_NUM_CTX`（默认 8192，范围 2048–32768）和 `OLLAMA_KEEP_ALIVE`（默认 `15m`，范围 1–60 分钟），避免两条路径使用不同上下文而重新装载。参见 [Ollama 预加载及驻留说明](https://docs.ollama.com/faq)。
- 普通 Ollama 生成预算为 240 秒，远程为 90 秒；检索预算 30 秒。Agentic 总预算相应为 270/120 秒，浏览器允许 285 秒，API `maxDuration` 为 300 秒。保留用户取消和有限截止期限，不无限重试。
- `pnpm dev` 选择实际可用端口；显式 `PORT` 不可用时说明原因。端口监听单独检测（60 秒），随后用一次有完整 180 秒预算的 GET 验证 `/api/health/live`，避免每两秒取消冷编译请求。再以无副作用 OPTIONS 请求串行预编译问答、模型选择和加载接口，每个接口有 180 秒期限。健康/预编译未完成会明确提示具体接口、资源排查上下文和“尚未就绪”，保留已监听的开发服务以便修复；只有全部验证通过才提示可以提问。Next.js 进程退出时取消尚未完成的探测，并保留进程退出原因。
- 2026-10-09 启动检测修复验证：18 项启动回归分别在 Node 22.22 和 Node 24.19 上通过，覆盖超过两秒的真实健康响应、响应体停滞、预编译超时后子服务仍可访问以及进程退出取消。完整一键启动验证通过：健康接口冷编译 16.8 秒，问答 89 秒，模型选择 4.9 秒，预加载 26.6 秒。启动后的真实日期、时间和计算请求均返回 200，分别耗时 42、37、7 毫秒。这些数值是本机样例，不是性能保证。
- Windows postbuild 检查并修复 standalone 包目录的符号链接类型，保留相对链接；仅清理工作区内已确认的旧 standalone 输出。发布追踪检查覆盖文档搜索路由，排除原始源码和测试文件，不排除运行时资源。
- 构建使用 Next 随附的 [Vercel Node File Trace](https://github.com/vercel/nft) 从 SDK 原生入口追踪依赖闭包，补齐 CommonJS 导出及其递归依赖；同时携带 Windows Sharp/ONNX 的配套动态库。`check-standalone-runtime.mjs` 在发布包内真实加载 SDK，并拒绝依赖回落到开发目录，避免生产 RAG 请求才发现缺包。

预加载可以将冷启动移到提问之前，不能让磁盘读取和模型迁移消失。本机日志曾显示 Ollama 的 GLM GGUF 迁移耗时约 14 分钟，导致两次加载中断；迁移结束后，同一模型以 8192 上下文装载成功，耗时 187.6 秒。模型位于机械硬盘，GPU 16 GB，Ollama 报告 26% CPU / 74% GPU 分配。因此必须区分“选择已应用”“正在加载”和“已准备”，不能仅以模型名变化宣称模型可用。

```powershell
pnpm test:conversation-routing
node --test src/app/api/ask/route.test.mjs

```

直接运行 TypeScript 的回归测试需要 Node 24，与项目 CI 保持一致。

测试从 [CLINC150 官方数据集](https://github.com/clinc/oos-eval) 选取少量日期、时间、计算、天气与问候样例（Larson 等，EMNLP 2019），另有项目自编的中文改写、复合请求、权限及文档反例。这是项目回归集，不能将其通过率声称为完整 CLINC150 或开放域准确率。

2026-10-09 本机验证记录：相关回归 212 项通过，新增的 SDK 追踪、复制、加载顺序和串行预编译 5 项回归也通过，类型检查和生产构建通过。全新 standalone 的项目原始源码/测试残留为 0；SDK 检查确认没有回落到开发目录。生产接口的日期、时间、计算和当前模型查询分别为 23、3、4、2 毫秒；不常见的时间问法经分类器处理由 1.06 秒降至热请求 152 毫秒。后台加载入口在 251 毫秒内返回 `loading`，GET 随后观测到 `ready`。GLM 的“根据知识库，远大前程探讨了哪些主题？”真实问答最新总耗时 16.3 秒，检索证据 3 条；另一次 23.5 秒的回答已核对四个主题与 `sample7.txt` 中对应证据一致。开发服务重启后的串行接口预编译实测 9.7 秒完成，开发环境的日期、时间、计算和模型查询也通过真实 POST 验证。此前可用内存不足 2 GB，且 Next 文件系统缓存整理耗时 84 秒；开发首次编译超过了预热期限。资源释放后串行预编译完成，启动失败仍会明确报告接口和资源上下文。这些数值只代表本机样例，不是延迟保证。

[LangChain 路由文档](https://docs.langchain.com/oss/javascript/langchain/multi-agent/router)介绍按输入分类并选择处理路径；本项目优先使用可验证、无需等待模型的能力解析，继续保留既有知识库策略和安全边界。

本轮模型列表与向量切换修正的验证：268 项相关回归通过，涵盖界面选择、后台任务、隔离范围、强一致数量核对、失败回退、持久化恢复及既有问答路由。真实 Ollama 列表中 `glm-4.7-flash:latest` 合并为 1 项，内部 runner 为 0 项；不同标签保持独立。真实 42 块知识库完成 `nomic-embed-text`（768D）→ `bge-m3`（1024D）→ `nomic-embed-text`（768D）切换。BGE 问答返回 3 条证据；全新 standalone 进程恢复了 BGE 配置，并成功完成切回原模型，入口响应 94 毫秒。原集合保留。构建、类型及发布依赖/源码追踪检查通过。

读取快照采用 [Milvus 迭代器](https://milvus.io/api-reference/node/v2.6.x/Vector/queryIterator.md)；当前安装的 SDK 在内部计数中未传递模板参数，因此只使用服务端范围生成的安全字面量，并核对强一致源数量。发布前同样使用强一致逻辑计数，避免将尚未更新的集合统计值（本机曾为 8，而实际已写入 42）当作索引完整性依据。
